# Gym sync contract v1 (shared between server and Android app)

Binding for both sides. Server = the sync server. App = Android client.
JSON everywhere, snake_case keys, UTF-8, timestamps ISO-8601 UTC with `Z`, weights in kg (float), ids are strings.

## Entities (document-level sync)
Each synced record is a **document**: `{ "id", "entity", "rev", "updated_at", "deleted", "origin", "data": {...} }`.
- `id`: UUID v4 string generated by whoever creates it (app or server). Legacy ids from the old app are kept verbatim.
- `rev`: integer, server-assigned, globally monotonic (one counter for all entities). Client never invents revs.
- `deleted`: tombstone flag (true → `data` may be `{}`).
- `origin`: `"app"` | `"server"` | `"import"`.

Entity names and `data` fields (all optional unless marked *):

| entity | data |
|---|---|
| `gym` | name*, short_name, archived(bool), has_sauna(bool), notes, sort_order(int), packlist: [{id*, text*, order*, done_default(bool)}], color ("#rrggbb"), subtitle |
| `exercise` | name*, aliases[], equipment, category, primary_muscles[], secondary_muscles[], instructions[], measurement_type*, load_direction*, load_basis*, movement_family, photo_ref (string; photo bytes are NOT synced in v1), notes, muscle_groups[], muscle_subgroups[] |
| `plan` | name*, notes, created_at, archived(bool), changed_by_assistant_at, change_summary, exercises: [{id*, exercise_id*, order*, mode_sets{normal,fast,ultra}*, target{metric,min,max,rir_min,rir_max}*, starting_weight_kg, current_weight_kg, rest_seconds*, superset_group, notes}] |
| `machine_profile` | gym_id*, exercise_id*, available_weights_kg[], weight_ranges[{id,min_kg,max_kg,step_kg}], setup_parameters[{id,name,value}], machine_brand, machine_model, notes, addon_weights_kg[] |
| `session` | gym_id, plan_id, plan_name*, mode* (normal/fast/ultra), status* (active/completed), started_at*, completed_at, duration_seconds, notes, import_key, focus_exercise_id (amendment F), exercises: [{id*, source_plan_exercise_id, exercise_id*, name*, order*, notes, measurement_type, load_direction, load_basis, target{...}, rest_seconds, superset_group, planned_sets, suggested_weight_kg, suggestion_reason, sets: [{id*, order*, set_type* (working/warmup), status*, weight_kg, addon_weights_kg[], reps, seconds, meters, effort, set_duration_seconds, rest_before_seconds, setup_before_seconds, completed_at}]}] |
| `workout_adjustment` | session_id*, status* (pending/applied/rejected), reason*, created_at*, resolved_at, status_reason, ops[]*, op_results[] (amendment D) |
| `day_workout` | id `day-<date>`; date* (YYYY-MM-DD, local day), gym_id*, title*, note, exercises[]* (plan exercise objects), packlist[] (like gym packlist), status* (offered/started/dismissed/expired/withdrawn), created_at*, resolved_at, session_id (amendment E) |
| `body_weight` | date* (YYYY-MM-DD), weight_kg*, notes |
| `milestone` | plan_id, plan_exercise_id, exercise_id*, exercise_name, session_id, occurred_at*, previous_weight_kg, new_weight_kg*, direction, seen(bool) |
| `goal` | singleton with id `weekly`: training_days_per_week (1–7), target_sets{brust, schultern, arme, beine, bauch, ruecken: 0–60}, updated_by (`app`/`server`) |

Enum values are exactly those of the old app (measurement_type: load_reps, bodyweight_reps, added_weight_reps, assisted_reps, reps_only, load_duration, load_distance_duration, duration_only; load_direction: higher, lower_assistance, none; load_basis: stack,total,per_hand,added,assistance,none; effort: limit, one_two, three_four, five_plus + legacy one, two_three, four_plus; set status: pending, completed, skipped_time, skipped_equipment, failed, pain, skipped_other).
Unknown extra fields in `data` must be preserved (round-trip), never dropped.

**Test profile is local-only**: the app never syncs test-profile data.
**Active sessions** (`status=active`) are pushed too (crash safety, and so that the server can show where the user is), but the server never edits an active session; it can only ask for changes (amendment D).

## Endpoints (base URL configured by the user at pairing; HTTPS only)
1. `POST /gym/v1/pair` body `{ "code": "<one-time code>", "device_name": "..." }` → `200 { "token": "<opaque>", "device_id": "..." }`. Wrong/expired code → 401 `{ "error": "invalid_code" }`. Rate-limited (429).
2. All other calls need `Authorization: Bearer <token>`. Missing/invalid/revoked → 401 `{ "error": "unauthorized" }`.
3. `GET /gym/v1/snapshot` → `{ "rev": N, "documents": [ ...all non-deleted documents... ] }`.
4. `GET /gym/v1/changes?since=<rev>&limit=<1..500, default 500>` → `{ "changes": [documents incl. tombstones, ordered by rev asc], "next_since": M, "has_more": bool }`.
5. `POST /gym/v1/push` body `{ "ops": [ { "op_id": "<uuid>", "entity", "id", "op": "upsert"|"delete", "base_rev": <int|null>, "client_updated_at": "<ts>", "data": {...} } ] }` (max 200 ops, max 2 MB) →
   `{ "results": [ { "op_id", "status": "applied"|"conflict"|"rejected", "document": <current server document or null>, "reason": "<code, on rejected>" } ], "rev": N }`.
   - Idempotent by `op_id` (replay returns the same result).
   - `base_rev` null = create. If the doc exists and `base_rev` < current rev → **conflict**: newer `client_updated_at` vs server `updated_at` wins; result `conflict` with the winning document; the losing version is kept server-side (undoable). For `session` docs the app's version always wins unless the server-side doc was edited after `completed_at` (then conflict rule applies).
   - Validation errors → `rejected` with reason (e.g. `invalid_field`, `unknown_entity`, `too_large`).
6. `POST /gym/v1/telemetry` body `{ "counts": [ { "day": "YYYY-MM-DD", "screen", "element", "count": int } ] }` (max 1000 rows) → `{ "ok": true }`. Server adds counts (idempotent by including `batch_id` uuid at top level).
7. `GET /gym/v1/status` → `{ "rev": N, "server_time": ts, "device_last_seen": ts }` (cheap check before sync).

## Sync algorithm (app)
1. Push outbox (ordered), apply results (replace local doc with returned `document` on conflict; surface a non-blocking notice).
2. Pull `changes` since stored cursor until `has_more=false`; upsert/delete locally; store `next_since`.
3. First run / cursor invalid (410 `{error:"resync_required"}`) → `snapshot`.
Triggers: app start, after finishing a session, periodic (WorkManager, network required), manual button. Persist `last_successful_sync_at` for the UI.

## v1 amendment A (2026-11-02): weights strictly per gym
Problem in the old app: `current_weight_kg` lived on the plan exercise (gym-agnostic) → weights of different gyms (different cable ratios) mixed; wrong gym selection polluted history.
Rules (binding for server + app):
1. **Working weight and progression are per gym × exercise.** New fields on `machine_profile` (one per gym_id × exercise_id): `working_weight_kg`, `working_weight_updated_at`, `working_weight_source_session_id`. `plan.exercises[].current_weight_kg` / `starting_weight_kg` become legacy/fallback only (kept for round-trip, never updated by new progression).
2. Progression input = only completed sessions with the same `gym_id` (and same exercise_id, with the existing sourcePlanExerciseId→exerciseId fallback). Weight suggestions are rounded to that gym's available levels.
3. **Cross-gym start estimate** (first time an exercise is done in a gym, i.e. no same-gym history): estimate from other gyms' data. Algorithm `estimate_start_weight(exercise_id, target_gym, history, machine_profiles)`:
   a. If there exist paired observations of this exercise in target_gym and another gym G (sessions within 14 days of each other, both completed working sets) for *any* exercise sharing the same equipment/load_basis → learn ratio r = median(weight_target/weight_G) over those pairs; estimate = r × proven working weight in G.
   b. Else estimate = proven working weight from the most recent other gym × 0.85 (conservative).
   c. Round DOWN to target gym's available levels. If no data at all → existing guided starting estimate.
   Result carries `suggestion_reason = "cross_gym_estimate"` and `suggestion_source_gym_id`.
4. **Session gym is required** for new sessions (`gym_id` non-null; "other" allowed). The app forces an explicit gym confirmation at session start.
5. **Reassign gym afterwards**: changing a completed session's `gym_id` (app or server tool) triggers recalculation of `working_weight_kg` for all affected gym×exercise pairs (old and new gym). Server: an operation that changes a session's gym; App: action in the history detail.
6. **Legacy import flags**: importer copies everything unchanged but adds `data.review_flags: ["gym_suspect"]` to sessions whose working-set weights don't fit that gym's machine profile levels or deviate >30 % from the same exercise's median in that gym (and `"gym_missing"` where gymId was absent → basic_fit default). The server exposes flagged sessions for review; clearing a flag = removing it from `review_flags`. App shows a small "zu prüfen" badge.
7. Golden tests for per-gym progression, cross-gym estimate (a/b/c), and gym reassignment must exist on BOTH sides with identical cases (JSON format {name, fn, input, expected}).

### Reference semantics used by both implementations (details of rules 2, 3 and 5)
- **Working weight replay** (`recalculate_working_weights`): completed sessions with a non-null `gym_id`, ordered by `completed_at` (else `started_at`), ties by document id. For every performed exercise the key is `(gym_id, exercise_id)`; the new weight is `proven_working_weight(exercise, previous)` (two qualifying working sets in one session, previous = current weight of that key or none). `working_weight_source_session_id` is the session that last changed it, `working_weight_updated_at` its completion time. Active and gym-less sessions are ignored. A key without proof has no working weight (fields removed).
- **Cross-gym estimate applies only if the target gym has no completed working-set data for the exercise.** Source gym G = the other gym with the most recent completed session containing the exercise. Working weight in G = replay result for `(G, exercise)`, else the most frequent working weight of the latest session there.
- **Ratio (a):** for every session pair (target gym, G) whose `started_at` dates are at most 14 days apart and every exercise sharing `equipment` and `load_basis` with the target exercise (including itself) that has working-set weights in both, ratio = median(weights in target session) / median(weights in G session). r = median of all ratios (mean of the two middle values for an even count). Estimate = r x working weight in G. **(b)** without ratios: working weight in G x 0.85. **(c)** round DOWN to the target gym's available levels (the smallest level if all are above; 0.5 kg steps if the machine has no levels).
- **Start weight priority** for a new session exercise: stored `working_weight_kg` of the gym machine profile, latest same-gym workout, cross-gym estimate, guided related-exercise estimate, legacy plan weight. `suggestion_reason` values: `gym_working_weight`, `gym_history`, `cross_gym_estimate`, `guided_estimate`, `plan_weight`; `suggestion_source_gym_id` is set for `cross_gym_estimate`.
- **Gym id `other`** is the placeholder for a place that is not a configured gym.
- **Reassigning** a completed session's gym recomputes the weights of both the old and the new gym for all exercises of that session; the app also removes the `gym_suspect`/`gym_missing` flags because the gym was confirmed by the user.
- Golden cases for these functions are in `core/src/test/resources/progression_golden.json` (`recalculateWorkingWeights`, `estimateStartWeight`, `reassignSessionGym`).

## v1 amendment B: single device, device-key signatures, no fingerprinting

Goal: knowing the server address gives an attacker nothing; only one phone has access.

1. **Single device.** The server allows at most one active (non-revoked) device. Pairing while an active device exists is impossible (same response as below); the owner revokes the device first, or requests a pairing code that replaces it (the old device is revoked only when the new pairing completes).
2. **Pairing window.** `POST /gym/v1/pair` exists only while an unexpired, unused pairing code exists; otherwise it answers with the neutral 404. Codes are at least 10 characters from an unambiguous alphabet, expire after 10 minutes, are single use, and a global lockout applies to wrong attempts.
3. **Device key (proof of possession).** At pairing the app generates an EC P-256 key pair in the Android Keystore (non-exportable; StrongBox if available, otherwise the TEE; no user-authentication requirement because syncing runs in the background) and sends the public key in the pair request: `{ "code", "device_name", "public_key" }` with `public_key` = SubjectPublicKeyInfo (X.509 DER), base64url without padding. Every authenticated request carries:
   - `Authorization: Bearer <token>`
   - `X-Gym-Timestamp`: unix seconds (the server accepts +/- 300 s)
   - `X-Gym-Nonce`: at least 16 random bytes, base64url without padding (the server rejects reuse within 10 minutes)
   - `X-Gym-Signature`: base64url (no padding) ECDSA-P256-SHA256 signature, DER encoded, over the canonical string

   ```
   METHOD \n PATH \n QUERY \n TIMESTAMP \n NONCE \n SHA256_HEX(body)
   ```
   `METHOD` upper case; `PATH` is the request path without host (including any path prefix of the configured base URL); `QUERY` is the raw query string without `?` (empty if none); `SHA256_HEX` is the lower-case hex SHA-256 of the exact request body bytes (of the empty string for requests without body). Test vector: `GET`, `/gym/v1/changes`, `since=5&limit=500`, `1700000000`, `AAAAAAAAAAAAAAAAAAAAAA`, empty body gives
   `GET\n/gym/v1/changes\nsince=5&limit=500\n1700000000\nAAAAAAAAAAAAAAAAAAAAAA\ne3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`.
   A token alone, or a signature by another key, is rejected.
4. **No fingerprinting.** Every unauthenticated or invalid request to any `/gym/v1/*` path (missing/invalid token, bad signature, stale timestamp, replayed nonce, revoked device, unknown path, closed pairing window) gets the same response: HTTP 404 with the server's generic not-found body, no protocol-specific headers, and similar timing. Details are only logged server-side. Flooding with unauthenticated requests leads to a temporary global lockout of the whole `/gym/v1` area.
5. **Lifecycle.** A device expires after 120 days without a successful request (the app pairs again). The owner can revoke the device at any time; there is no undo besides pairing again.
6. **Scope.** The device credentials grant access to the gym documents and telemetry endpoints only.
7. **Client behavior.** A 404 on an authenticated call after a sync had already succeeded is shown as "Verbindung getrennt – neu koppeln" (re-pair). Automatic retries use exponential backoff (15 minutes, doubling, at most 24 hours); the manual "sync now" button may still try. A 404 on the pair request means pairing is currently not possible. Unpairing in the app deletes the token and the device key.

### Client note: machine profiles
The server may create a `machine_profile` with its own UUID for a gym x exercise. Before the app creates one it looks up an existing profile by (`gym_id`, `exercise_id`) among its local documents and updates that one; with duplicates the lowest id is used.

## v1 amendment C: data for the redesigned app

1. **Gym identity.** `gym.data.color` (optional `#rrggbb`) is the identity stripe colour, `gym.data.subtitle` an optional short line. The app falls back to a neutral grey and never hardcodes gym names, ids or colours.
2. **Add-on weights.** `machine_profile.data.addon_weights_kg` holds 0 to 2 positive numbers. The add-ons selected for a set are stored in `sets[].addon_weights_kg` (a subset). `sets[].weight_kg` stays the **total** (main level plus selected add-ons), so progression is unchanged. Rounding candidates are every main level plus every subset of the add-ons; values are rounded to the nearest candidate (or down, where the rule says so). Golden cases `weightCandidates`, `roundDownToCandidate` and `splitTotal` in `progression_golden.json` pin the behaviour on both sides.
3. **Goal.** Entity `goal` with the fixed id `weekly`: `training_days_per_week` (1–7), `target_sets` per radar area (0–60) and `updated_by`. It is editable in the app (Mehr › Ziele) and by the server.
4. **Muscle groups.** `exercise.data.muscle_groups` is an array from the fixed set `brust, ruecken, unterer_ruecken, schultern, bizeps, trizeps, unterarme, bauch, quadrizeps, beinbeuger, gesaess, waden`; the first entry is the primary group. Radar areas: Brust = brust; Schultern = schultern; Arme = bizeps + trizeps + unterarme; Beine = quadrizeps + beinbeuger + gesaess + waden; Bauch = bauch + unterer_ruecken; Rücken = ruecken. A completed working set counts 1 for the primary group and 0.5 for every further group. Without `muscle_groups` the groups are derived from `primary_muscles` / `secondary_muscles` with a fixed table (`android/core/src/main/resources/muscle_mapping.json`; legacy catalog names to the twelve groups).
5. **Plans changed by the assistant.** The server sets `plan.data.changed_by_assistant_at` and `plan.data.change_summary` (one sentence). The app shows a notice until the plan is opened once; that seen state is stored on the device only.

## v1 amendment D: adjusting a running workout, manual working weight

Goal: Claude can adjust the workout while Jonathan is training, without the server ever editing a session. Claude leaves a
request, the app applies it to its own session and reports the result.

1. **Entity `workout_adjustment`** (created by the server, `origin` `server`; the app only changes the status fields).
   `data`: `session_id`* (the active session it is meant for), `status`* (`pending` | `applied` | `rejected`), `reason`*
   (one short sentence, max 300 characters, shown to the user), `created_at`*, `ops`* (1 to 10, below), and written back by the app:
   `resolved_at`, `status_reason` (short code: `no_active_session`, `session_finished`, `nothing_applied`, `undone`),
   `op_results` `[{index (0-based), status ("applied"|"skipped"), reason (code, on skipped)}]`.
   Operation object: `action`* plus `session_exercise_id` (the exercise inside the session), `exercise_id`/`exercise_name`
   (catalog exercise; `exercise_name` is informative), `weight_kg`, `reps_min`, `reps_max`, `sets`, `rest_seconds`, `position`
   (1-based), `text`, and for `add_exercise` `measurement_type`, `load_direction`, `load_basis` (so the app needs no catalog lookup).
   Actions: `set_weight` (total kg for every open working set), `set_reps` (target min/max), `set_sets` (total number of working
   sets), `set_rest` (rest seconds), `add_exercise`, `skip_exercise`, `move_exercise`, `note` (exercise note, or only a hint
   without `session_exercise_id`). Unknown fields are preserved like everywhere.
2. **The server never edits a session.** It validates against the synced active session, stores the adjustment as `pending` and
   leaves the rest to the app. A server-side undo (`tess_undo`) of a still pending adjustment removes it; once the app has
   written a status the undo is a conflict.
3. **App rules.** The app applies pending adjustments in document order, only to its active session (`session_id` must match; a
   missing, finished or other session gives `rejected`/`no_active_session` resp. `session_finished`) and only to unlogged
   sets: a completed, skipped or failed set is **never** changed, exercises without open sets are skipped (`skipped`, reason
   `finished`), `set_sets` only adds or removes open working sets (never below the number of handled sets), `skip_exercise`
   only an exercise without logged sets, `move_exercise` only exercises with open sets (as in the manual editing of the
   session). `set_weight` sets `suggested_weight_kg` and `suggestion_reason` `"assistant"` on the exercise; the weight is the total.
   Status `applied` when at least one operation changed something, else `rejected`/`nothing_applied`. The user can undo an applied
   adjustment; the app then writes `rejected`/`undone` (the changes are reverted except sets logged meanwhile).
4. **Sync during a workout.** While a session is active the app syncs about every 45 seconds (the cheap `status` check first;
   after errors the interval grows up to 5 minutes, and the reconnect backoff of amendment B still applies) and when it is opened.
   This pushes the active session (so the server can show where the user is, read only) and pulls adjustments; applied results are
   pushed right away. Without a workout the usual triggers apply.
5. **Manual working weight.** A machine profile whose `working_weight_source_session_id` is `"manual"` (set by the server on
   request, with `working_weight_updated_at`) is a baseline for the replay of `recalculate_working_weights` for that gym x exercise:
   sessions up to `working_weight_updated_at` count as before (milestones included), the first later session continues from the
   manual weight, and without later sessions the manual weight stays. Both implementations (server and app, also gym reassignment
   and editing finished sessions) use this rule; golden cases `recalculateWorkingWeights` with `baselines` pin it.

## v1 amendment E: one-off workout for a day (`day_workout`)

Goal: Claude builds a workout in the chat for one specific day (with gym and what Jonathan needs to bring). It is **not** a plan and
is not kept as one: the app offers it on "Heute" on that day, starts a normal session from it with one tap and reports back.

1. **Entity `day_workout`**, id `day-<date>` (so at most one per day; a new one for the same day replaces it), created by the server
   (`origin` `server`); the app only changes the status fields. `data`: `date`* (`YYYY-MM-DD`, Jonathan's local day), `gym_id`*,
   `title`* (max 200), `exercises`* (1 to 40, **the same objects as plan exercises**: `id`, `exercise_id`, `order`, `mode_sets`, `target`,
   `starting_weight_kg`, `rest_seconds`, `notes`, ...), `packlist` (extras for this workout, objects like the gym packlist: `id`, `text`,
   `order`; the gym's own packlist is shown anyway), `note` (message to Jonathan, max 2000), `status`*, `created_at`*, and written back by
   the app: `resolved_at`, `session_id` (the session that was started). Unknown fields are preserved like everywhere.
2. **Status.** `offered` (server, initial) -> `started` (app: a session was started from it; `session_id`, `resolved_at`) | `dismissed`
   (app: the user hid it) | `expired` (app: `date` is over and it was never started) | `withdrawn` (server: Claude took it back).
   A new server write for the same day sets `offered` again and drops `resolved_at`/`session_id`, except after `started` (then the
   server refuses). The app offers only `offered` documents whose `date` is today; a document with `date` before today is treated as
   `expired` even before the app has written that (after each sync the app writes `expired` for such documents).
3. **App rules.** Starting works like starting a plan with mode `normal` (`mode_sets.normal` sets per exercise) in the gym of the
   document (shown on the card, which is the explicit confirmation of the gym; another gym can be chosen). The session gets
   `plan_id` = null, `plan_name` = `title`, and the extra fields `source` = `"day_workout"` and `day_workout_id`. Start weights follow
   the usual order (gym working weight, history, estimates); `starting_weight_kg` is only the last fallback like the plan weight.
   Progression, working weights and milestones therefore work per gym x exercise exactly as for plan sessions. With a running
   session nothing new is started (the card is hidden while a session runs, "Training läuft" is shown instead). The checked state of the
   extra packing items is local only (settings key `pack:day:<document id>`, valid for the day like the gym packing list).
4. **Not a plan.** Nothing is written to the `plan` entity; the document is not listed with the plans and has no effect on the plan
   recommendation. Sessions with `source` `day_workout` have no plan id, so the plan-based statistics skip them (the per gym x exercise
   statistics include them).

## v1 amendment F: focus exercise, adjustment cleanup

1. **Focus exercise.** The `session` document has an optional field `focus_exercise_id` (string, a `session.exercises[].id`): the exercise the user currently has open on the training screen (after jumping with the exercise strip). Absent or `null` = no focus, i.e. the first exercise with an open set. The app writes it into the active session when the focus changed, right before each run of the workout sync loop (about every 45 s, `WorkoutActions.publishFocus`, pure rule `withSyncedFocus` in `:core`); an id that is not an exercise of the session counts as none. The focus itself stays in memory in the app (a restart means "first open"); the server never writes the field and uses it only for display (`tess_get_gym` shows it as the current exercise). Unknown-field safe: other clients keep it when rewriting the session, and an unknown or stale id must be tolerated. Only meaningful while `status` is `active`.
2. **Cleanup of `workout_adjustment`.** The server removes old adjustments with ordinary tombstones (`deleted`, via `/changes`): resolved (`applied`/`rejected`) ones 30 days after `resolved_at`, and `pending` ones older than 7 days whose session is no longer active. The app treats them like any other deleted document (drops its local copy); it must not resurrect a deleted adjustment by pushing it again.

## v1 amendment G: muscle subgroups (finer muscle map)

Protocol (identical in the app's `android/docs/sync-protocol.md` and the server's `docs/gym-sync-protocol.md`): the `exercise` document has an optional field `muscle_subgroups` (array of strings, keys from the fixed set below, order irrelevant). It refines the muscle map only: the counting rule, targets, radar and statistics stay on the twelve `muscle_groups`, a subgroup's sets are part of its parent group (parent sets = sum of the subgroups' shares plus the sets of exercises that name none of that group's subgroups).

| subgroup | parent group |
| --- | --- |
| `brust_oben`, `brust_unten` | `brust` |
| `schulter_vorne`, `schulter_seitlich`, `schulter_hinten` | `schultern` |
| `latissimus`, `rhomboiden`, `trapez_oben`, `trapez_unten` (trapezius middle/lower) | `ruecken` |
| `bauch_gerade`, `bauch_schraeg` | `bauch` |
| `abduktoren` | `gesaess` |
| `adduktoren` | `quadrizeps` |

Rules: a subgroup belongs to its parent, which should be in the exercise's `muscle_groups`; a subgroup whose parent is not among the exercise's groups is ignored by the app. If an exercise names several subgroups of one group, the group's weight (1 primary, 0.5 further) is split evenly among them. An exercise without `muscle_subgroups`, or without one for a group, colours the whole group on the map as before. Unknown-field safe in both directions: older clients ignore the field and keep it when they rewrite the document; clients skip subgroup keys they do not know, so the set may grow later. Absent and `[]` mean the same.

The app reads it in `Exercise.muscleSubgroups` and aggregates in `summarizeMuscles(..., subgroupsOf)`; the key table is `core/model/MuscleSubgroups.kt` and `subgroups` in `core/src/main/resources/muscle_mapping.json` (a test keeps both identical). It never writes the field.
